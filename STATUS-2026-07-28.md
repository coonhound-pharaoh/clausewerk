**B11 explained**, because its resolution is the unusual one. The check was named "an outage
is blamed on the caller". Deleting the code it protects does *not* blame the caller — the
error falls through to the general handler, which also reports a service failure and also
hides the technical detail. Both things the test checks stay true. What is actually lost is
one sentence being more specific, and this repository does not test wording. So the check was
misnamed rather than the code broken, and it was retired rather than given something invented
to guard. If an outage is ever made observably different — a screen saying "try again
shortly" instead of "something broke" — the check should come back guarding that.

**A-2 explained**, because it is the one with real-world consequences. A session key is a
bearer credential — whoever holds it *is* that person, with nothing in the audit trail telling
them apart from the real holder. The table used to store those keys word for word, so every
backup, replica and database console session was a set of working logins for everyone signed
in. The table now stores a fingerprint instead: it can confirm a key someone presents, and it
cannot produce one. A copy of the table is no longer worth stealing.

**Nobody was signed out.** Verified end to end against a throwaway database: a session was
planted with its key in the clear, the migration applied, and the same key still signed in
afterwards. That property is why doing this now was cheap — the same change against a customer
database with live sessions would have meant a company-wide forced sign-out.

A-1 and A-2 look alike and are not. A-1 stopped the wrong *role* reading the table; it could do
nothing about a *copy* of the table, and a backup is a copy. Both were needed.

**A-3 explained**, because the fix is a one-line predicate but the reason it took care is
worth keeping. Expired sessions were being kept out by a `DELETE` whose own comment describes
it as housekeeping — tidying up abandoned rows so the table doesn't grow. The lookup beside it
checked nothing. It worked, but the entire expiry guarantee was resting on a statement anyone
could reasonably move to a scheduled job for performance, at which point every expired session
would quietly start working again. The lookup now checks expiry itself; the sweep goes back to
being housekeeping, which is all it ever claimed to be.

Three things fell out of testing that properly, and they are the same lesson B11 taught:
the obvious test passed whether or not the fix was there (the sweep hid it), so the test had
to read a session row the sweep had never touched; the obvious way to break the code for
testing made every test fail for the *wrong* reason, which proves nothing; and two of my own
tests turned out to be controls rather than guards — one of them named as though it proved
something it didn't. They are relabelled. The mutation check that watched this was repointed
too, because after the fix it was watching the wrong statement.

**D-2 explained.** A test that hammers the session store from eight threads at once had its
iteration count quietly cut from 200 to 50 — quartering the chance of catching the very thing
it exists to catch, while the report still said it was watching. A concurrency test made a
quarter as likely to fire is worse than one that was deleted, because a deleted test is
visibly gone. Restored, and timed rather than guessed: the reduction saved about four seconds
and bought nothing. Its description had also been softened to "handles concurrent
modifications", which names no failure at all; it now names the four specific database
failures it hunts. And 58 accounts that only this one test used have moved out of the shared
setup that claimed to serve everything.

One honest limit, written into the test: this is a stress test, not a proof. A green run means
"did not reproduce", never "cannot happen". That is precisely why the iteration count was
worth arguing about.

**Also closed:** the migration ledger now records a checksum. Editing an already-applied
migration used to be skipped in silence on every database that had run it, forever. Proven
both ways against a throwaway database: caught with the checksum, silently skipped without.
It cannot speak about the past — rows predating the column are given a baseline from the
files as they are now, and it says so rather than claiming a clean bill of health.

## Open

**Nothing.** Every defect in `bug_report.md` and every finding in `audit_results.md` is closed.

The two housekeeping items are closed too:

**The session table now has SQL-side tests.** `db/test/session.test.mjs`, 16 checks. This
matters more than it sounds: the guarantee lives in the database, so a Python test cannot fail
if someone widens the policy and never touches Python — which is exactly how A-1 arrived.
Verified as a real guard: with the fix removed, four of the sixteen fail.

**The other verification harness was checked** — by the concurrent session, who found it red
for the same reason ours was and repaired it. They also added a rule to `CLAUDE.md`: any
migration change must be followed by the SQL harness before committing. That was the largest
remaining unknown and it is now answered.

**Deferred deliberately, and still the right call:** real row-level security on the five
run-evidence tables. There is no live exposure — every current consumer resolves through a
protected table first — and the tripwire makes any new file naming them get read before it
merges. Revisit when someone actually builds a screen that takes a snapshot id.

## Notes for whoever picks this up

**Two sessions were writing this repository at once all day.** That is not a theory — the
other session claimed two `memory.md` entry numbers while this work was in flight, and
committed changes to migration files that had already been applied.

Two habits worth keeping:

1. **`memory.md` numbering: check the highest number in the file, not the last one in it.**
   They are not the same. That mistake was made once today; the entries are not in numeric
   order.
2. **Never edit an applied migration.** This is now enforced rather than merely conventional
   — the ledger records a checksum and refuses to start if a file has changed. If you get
   that refusal, supersede the migration with a new number; do not clear the checksum unless
   you have written down why.

**Recommendation:** commit this work on its own branch rather than straight onto `main`, so
the Phase 2 work and this remediation can be reviewed apart from each other.
