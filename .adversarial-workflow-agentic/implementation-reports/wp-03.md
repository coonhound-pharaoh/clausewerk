# WP-03 — Audit chain rebuilt (WP-03a / WP-03b / WP-03c)

Owner: single implementer, assignment `IMPL-WP-03`. Stage: Implementation (Gate 4).

---

## 1. Acceptance criteria — written before any code was edited

These are the criteria this package is measured against. Each is proved in §5.

1. **Session independence.** An honest, untampered chain verifies clean under at least three
   `TimeZone` values **and** three `DateStyle` values, where the reading session's setting is
   asserted to actually differ from the writing session's.
2. **Role rewrite detected.** Rewriting `actor_role` on a past row makes `cw.audit_verify()`
   report the tampered row.
3. **Truncation detected.** Deleting the newest rows is reported by the anchored checkpoint.
4. **Fork rejected.** Two rows claiming the same `prev_hash` are refused, and a second genesis
   row (a second NULL `prev_hash`) is refused.
5. **Confidentiality.** A `cw_requester` cannot read another actor's audit payload; an auditor
   can read everything.
6. **No collateral damage.** Every audited write still succeeds for every role that legitimately
   writes — tested **as each real role**, on the write path.
7. **Verify is green.** `cd backend && npm run verify` exits 0 with no `MISS` and no `IMPRECISE`.

Universal criteria U-A…U-E from `work-packages.md` also apply.

### Where each change lives, and why

- **`0001` edited in place** for everything that *replaces* broken logic: the pre-image, the two
  functions that use it, and the `security definer` marking. Redefining those functions again in
  `0007` would leave the broken definitions sitting in `0001` as a trap for the next reader, and
  the scheme would be documented in two places. No production data exists (OC §5 constraint 10),
  so there is nothing to re-anchor: every database is built from migrations, so no row written
  under the old pre-image survives anywhere. This is stated in the migration comment.
- **`0007` holds only genuinely new objects** — the unique index, the checkpoint table and its two
  functions, and the RLS policies. Nothing in `0007` redefines anything from `0001`.

## 3. What was done, per sub-package

### WP-03a — the pre-image

The old pre-image (`0001:78-81`, `:96-99`) hashed `new.ts::text` / `r.ts::text` and joined fields
with `'|'`. Replaced with a single shared function, `cw.audit_preimage(...)`, called by both the
writer and the verifier so the two can never drift apart. Changes:

- **`ts::text` → epoch microseconds.** `(extract(epoch from p_ts) * 1000000)::bigint::text`.
  `extract(epoch …)` is an absolute instant and does not render through `TimeZone` or `DateStyle`,
  so the writer and any later reader agree regardless of session settings.
- **`'|'` → length-prefixed framing.** `cw.lp(s) = octet_length(s) || ':' || s`. Length-prefixing
  is prefix-free: the reader knows how many bytes belong to a field before reading it, so no field
  content can shift a boundary. The demonstrated collision
  (`sha256('|a|b'||'|') = sha256('|a'||'|b|')`) is closed by construction.
- **`actor_role` added.** It is term 5 of the pre-image. It was stored (`0001:57`) but never
  hashed, so rewriting who did something was undetectable.
- **`seq` added.** Verified safe: `seq` is a `bigserial` default and is populated by the time a
  `BEFORE INSERT` row trigger runs.
- **`payload::text` kept.** `jsonb::text` is key-ordered and whitespace-normalised, so it is a
  stable pre-image term. This is now stated in the migration rather than assumed.

Field order is fixed and documented: `prev_hash, seq, ts_micros, actor, actor_role, actor_kind,
event_type, subject, payload`.

### WP-03b — fork guard and anchored tail

- **`unique index audit_no_fork on cw.audit_event (prev_hash) nulls not distinct`.** Two rows
  claiming the same parent are refused, and `nulls not distinct` means a second genesis row is
  refused too. Verified against false positives on legitimate append, truncate-and-reseed, and
  same-instant duplicate content (the red-team reproduction; re-checked here by running the full
  suite, which appends hundreds of audit rows across five suites without a single violation).
- **Advisory lock** `pg_advisory_xact_lock(...)` at the top of the append path. It is labelled in
  the migration as **untested** — PGlite is single-connection, so no test in this repository can
  observe its absence. It ships on reasoning alone; the unique index is the guarantee that is
  actually proved.
- **Anchored checkpoint.** `cw.audit_checkpoint(checkpoint_id, taken_at, height, last_seq,
  last_hash)`. `cw.audit_checkpoint_take()` records the current tail; `cw.audit_anchor_check()`
  reports `ok`, `no checkpoint`, or a description of what is wrong. Truncating the newest rows
  makes the checkpointed row disappear (or the count fall below the recorded height), which the
  hash chain alone cannot see. A checkpoint is taken at the end of `0007` so every database has an
  anchor from birth; deployments call `take()` on a schedule.
- **Honest limitation, written into the migration:** `pgcrypto` is unavailable in PGlite, so the
  checkpoint is **anchored but unsigned**. It catches accidental deletion, partial restores and a
  future non-owner DELETE grant. It does **not** survive an attacker who owns the database, because
  the same owner who holds DELETE on `cw.audit_event` can also rewrite `cw.audit_checkpoint`.

### WP-03c — row-level security

- RLS enabled on `cw.audit_event` (it had none: `relrowsecurity = false`).
- **SELECT policy** `audit_read_scoped`: `auditor`, `legal_reviewer` and `legal_admin` read
  everything; a `requester` reads only rows whose `actor` is their own. A viewer holds no grant and
  is refused before policies are consulted.
- **INSERT policy** `audit_append` — the trap. A SELECT-only policy makes **every audited write**
  fail with `new row violates row-level security policy` for requester *and* legal_admin, because
  `cw.audit()` is `security invoker` and inserts as the caller. The INSERT policy admits the three
  roles that hold the INSERT grant.
- **`cw.audit_verify()` is now `security definer set search_path = cw, pg_temp`.** Under RLS a
  scoped role walks a filtered view, so the invoker version reports tampering on an honest
  database. `cw.audit_anchor_check()` is `security definer` for the same reason.
- RLS is **enabled, not forced**. The table owner still bypasses it — that is deliberate: the
  migrations and every suite's seeding run as the owner. It is stated in the migration.

**The two inert candidates named in gate-3 §5 were handled, not shipped as written.**

- The **INSERT-policy mutation** (#5) would have passed against an owner-run write, because the
  owner bypasses row-level security entirely. Its test performs the audited write **as a real
  `cw_requester`** through `roles.mjs`. Confirmed `ok`.
- The **fork mutation** (#3) cannot be induced by an ordinary insert, because `prev_hash` is
  trigger-assigned. It is kept, and the test induces the fork the only way an attacker could — by
  disabling the trigger and inserting a second child of an existing parent directly. Confirmed
  `ok`. The mutation was not dropped.
- **No serialisation or concurrency mutation was added.** It would be guaranteed to miss in
  single-connection PGlite.

## 5. Evidence — each acceptance criterion, proved

`node db/test/audit-chain.test.mjs` → **23 passed, 0 failed**.

1. **Session independence.** Seven tests. The writer session is pinned to `TimeZone = Etc/GMT+6`,
   `DateStyle = ISO, MDY` before any event is written. Each reader case then asserts, before
   verifying, that (i) the session setting genuinely differs from the writer's and (ii) the
   timestamp genuinely renders differently — so the test cannot pass by accidentally reading under
   the settings it wrote under, which is how the originally specified test could have passed
   against unfixed code. Timezones: `UTC`, `America/New_York`, `Asia/Kolkata`. Date styles:
   `SQL, DMY`, `Postgres, DMY`, `German, DMY` — deliberately *not* `ISO, DMY`, which was shown not
   to trigger the old alarm at all.
2. **Role rewrite detected** — `rewriting actor_role on a past event is detected`. A requester's
   own act is promoted to `legal_admin` at the database level; `cw.audit_verify()` returns `1`.
3. **Truncation detected** — three tests. `before a checkpoint is taken the anchor says so, not
   "ok"`; `a checkpoint over an intact log reports ok`; `the hash chain alone cannot see a
   truncated tail` (this one asserts `audit_verify()` returns `null` after truncation, which is
   exactly why the anchor has to exist); `truncating the newest events is caught by the anchor`.
4. **Fork rejected** — `a forked append is refused`, `a second genesis row is refused`, and
   `legitimate appends still work after all of that` as the false-positive control. Both refusals
   assert the error came from `audit_no_fork` specifically, not from some unrelated constraint.
5. **Confidentiality** — `a requester cannot read another actor's audit payload` (buyer B sees
   zero rows for buyer A's `concession_recorded` event, while buyer A still sees their own);
   `an auditor can read everything` (count equals the owner's count); `a viewer still cannot read
   the audit log at all`.
6. **No collateral damage** — `every writing role can still record an audited act` runs for
   `requester`, `legal_reviewer` and `legal_admin`, each **as the real database role** via
   `roles.mjs`. Plus `a scoped role gets a clean verify`, which is the non-owner verify the

## 6. Things found that were not in the plan

**F-1 — Row-level security also filters the APPEND path's own tail read. This is the serious one.**
`cw.audit_chain()` reads `select hash ... order by seq desc limit 1` to find out what to link the
new row to. As a `security invoker` function under the new RLS it reads the **caller's filtered
view**. A `cw_requester` sees only their own rows, so on their first ever audited act the trigger
found nothing, concluded it was writing the very first event in the log, and started a **second
chain alongside the real one** — a silent fork on an ordinary, legitimate write.

Nobody predicted this. The plan, the red-team review and the work package all treated
`cw.audit_verify()` as the only function RLS would blind; the writer was never mentioned. Note what
happened next: the **fork guard from WP-03b caught it** — the write failed loudly with
`duplicate key value violates unique constraint "audit_no_fork"` instead of quietly forking the
log. The guard justified itself within an hour of being written.

Fixed by making `cw.audit_chain()` `security definer set search_path = cw, pg_temp`, with the
reasoning written into the migration. Mutation #6 guards it. **Downstream packages should note
this**: any function that reads `cw.audit_event` for a system purpose, rather than to show a user
their own data, now has to be `security definer`.

**F-2 — `mutation-check.mjs` silently corrupted every dollar-quoted mutation.** The harness applied
mutations with `sql.replace(find, repl)`. `String.prototype.replace` treats `$$` in the
*replacement* as an escape for a single `$`, so any replacement containing a PL/pgSQL function body
delimiter came out as `as $` and the mutated SQL failed to parse. The mutation then reported
`IMPRECISE` — "the suite failed, but not via the named test" — which reads as a badly written
mutation rather than as a harness bug, and would have led an implementer to weaken a perfectly good
check. Fixed by passing the replacement as a function, which makes it literal. One line, commented.
This affected no existing entry (none contained `$$`), so no previously-passing result changes.

**F-3 — a checkpoint at migration time would be decoration.** The migration runs against an empty
log, so an anchor taken there would record height 0 and prove nothing. `cw.audit_anchor_check()`
therefore returns `'no checkpoint'` until one is taken, and there is a test asserting that it says
that rather than `'ok'` — "we have not looked" and "we looked and it is fine" are different answers
and the function must not conflate them.

## 8. Honest limitations

1. **The advisory lock has zero test coverage and cannot get any here.** PGlite is
   single-connection, so no test in this repository can observe its absence, and a mutation on it
   would be guaranteed to miss. It ships on reasoning alone. This is stated in the migration
   comment in those words, not implied. The guarantee that *is* proved is the unique index on
   `prev_hash`.
2. **The checkpoint is anchored but unsigned.** `pgcrypto` is unavailable in PGlite, so there is no
   cryptographic seal on the checkpoint row. It catches accidental deletion, a partial restore, a
   broken backup, and any future non-owner DELETE grant. It does **not** stop the database owner,
   who holds DELETE on `cw.audit_event` and can equally rewrite `cw.audit_checkpoint`. Against that
   actor the anchor raises the bar; it does not close the door. Notarising checkpoints outside the
   database is a later phase.
3. **RLS is enabled, not forced** — the table owner still bypasses it, deliberately, because
   migrations and every suite's seeding run as the owner. So these policies are a wall against
   application roles, not against the owner. Same threat model as (2). Stated in the migration.
4. **`actor_role` is now tamper-evident but still self-asserted at write time.** The chain proves
   it was not changed *afterwards*; it does not prove it was true when written, because it comes
   from a client-settable session variable. That is WP-04's problem and is flagged there already.
5. **There is no re-anchoring path, and none is needed.** Changing the pre-image invalidates every
   previously stored hash. No production data exists and every database is built by replaying
   migrations from empty, so no row written under the old pre-image survives anywhere. Stated in
   `0001` rather than left as an inference.
6. **The requester read scope is "rows I wrote", not "rows about my agreements".** Simpler, and
   strictly tighter than agreement-ownership scoping. If a requester later needs to see legal's
   actions on their own deal, that is an additive policy branch — it would need `cw.owns_agreement`
   from `0003` and therefore would have to live in `0007` or later, not `0001`.
