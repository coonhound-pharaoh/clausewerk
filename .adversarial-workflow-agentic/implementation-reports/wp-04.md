Owner: single implementer, assignment `IMPL-WP-04`. Stage: Implementation (Gate 4).

## 1. Acceptance criteria — written before any code was edited

Per the Gate-3 remediation rule (§6), these were fixed here first and are not restated after the
fact.

1. **No self-elevation on a governed write path.** A real `cw_legal_reviewer` cannot become a
   `legal_admin` by setting `cw.role`. This has its own test and its own mutation.
2. **Attribution cannot be forged.** An audit event cannot be written naming a role the connection
   does not hold — or, where that is not fully achievable, the residual is stated explicitly and
   its limit is tested.
3. **No collateral damage.** Every legitimate role can still do its legitimate work, tested as the
   real role on the write path; all eight suites stay green.
4. **`ARCHITECTURE.md` §5** states, in plain language, what the identity scheme assumes about the
   connection layer and that it is incompatible with transaction-mode pooling.
5. **`npm run verify` exits 0** — no `MISS`, no `IMPRECISE`, no `SKIP`.

**All five are met.** Evidence per criterion is in §5.

## 3. What was actually done

### The accessor

`cw.app_role()` read `current_setting('cw.role')`. It now reads `current_user`:

```sql
select case current_user
  when 'cw_viewer'         then 'viewer'
  when 'cw_requester'      then 'requester'
  when 'cw_legal_reviewer' then 'legal_reviewer'
  when 'cw_legal_admin'    then 'legal_admin'
  when 'cw_auditor'        then 'auditor'
end
```

`current_user`, not `session_user`, because `set role` is what binds — WP-01's harness already
proves `set role` genuinely changes privileges and RLS. Deliberately **not** `pg_has_role()`: a
superuser is an implicit member of every role, so `pg_has_role` would hand the owner `legal_admin`,
which is the exact opposite of settled decision U3.

**Checked before adopting:** no `security definer` function in the schema calls `cw.app_role()`.
That mattered — inside a definer function `current_user` is the function's owner, so an accessor
built on `current_user` would silently return the wrong answer there. All six definer functions
(`cw.audit_chain`, `cw.audit_verify`, `cw.owns_agreement`, `cw.agreement_execute`,
`cw.audit_checkpoint_take`, `cw.audit_anchor_check`) use `cw.app_actor()` or nothing at all.

The JWT-claims variant is written into the comment as the production shape rather than built,
because nothing in this repository can verify a signature (same constraint as the unsigned
checkpoint in `0007`).

### The attribution binding — the `actor_role` residual, closed

The packet flagged that `actor_role` was still self-asserted at write time even after WP-03 hashed
it. The connection-derived role made this cheap, so **it is fixed rather than documented**:
`cw.audit()` fills `actor_role` from `cw.app_role()`, and a new restrictive INSERT policy now
requires any hand-written row to do the same. Before this, the three roles holding `INSERT` on
`cw.audit_event` could append a row naming any authority they liked.

### The owner mapping (U3), and the tests it moved

Settled default U3 applied as written: the owner maps to no application role, and owner-run
governed writes were migrated onto named roles. **No owner escape hatch was needed or added.**
Exactly three tests broke, all repaired by moving the write onto the real role:

- `registry.test.mjs` · *the actor and role are captured on every event* — now asserts attribution
  on a `clause_version` insert made by a real `cw_legal_admin`. Strictly stronger: it proves the
  recorded role is the one the connection holds, not one it claimed.
- `ladder.test.mjs` · *a rung concession has nothing to promote* — now runs as a real
  `cw_legal_admin` via `queryAs`, so the authority check no longer fires before the question the
  test is asking.
- `ladder.test.mjs` · *a requester cannot promote* — renamed to **a caller with no legal_admin
  authority cannot promote**, because it runs as the owner and that is now precisely what it
  tests. Its mutation `expect` string was repaired in the same package. A genuine real-role
  companion was **added**: *a requester cannot even call the promotion function*.

### One assertion changed — declared, not buried

`ladder.test.mjs` · *a legal reviewer cannot promote by claiming to be legal_admin* previously
asserted the refusal message contained `permission denied`, i.e. that the last wall standing was
the table privilege. That was correct *because* the spoofed variable walked past the authority
check. Now the authority check refuses first, so the message changed. Rather than relax the test,
**both walls are now asserted separately**: the function refuses with `only legal_admin may
promote` *and* the reviewer is separately proved to lack the privilege to write
`promoted_to_clause` by hand. Net: one more assertion than before, not one fewer.

### `roles.mjs`

`cw.role` is now dead machinery, so `become()` no longer sets it and `as()` no longer snapshots and
restores it. `cw.actor` is still live and is still snapshotted and restored, for the reason recorded
in the existing comment.

## 4. Residuals — stated loudly

1. **`actor` (the person's name) is still self-asserted.** There is no per-human database identity;
   the five roles are shared service roles, so the name arrives in `cw.actor`, which a client with
   SQL access can set to anyone. The **role** half is closed; the **name** half is not. Binding
   `actor = cw.app_actor()` in the policy was considered and rejected as theatre — the same client
   that sets the name would satisfy the check. Written into `0001` and `ARCHITECTURE.md` §5.
2. **Incompatible with transaction-mode pooling.** The scheme assumes one connection carries one
   authenticated identity. Transaction-mode pooling leaks `set role` and session settings between
   clients. Stated in `0001` and in `ARCHITECTURE.md` §5 in plain language.
3. **The scheme is a wall against application roles, not against the owner.** Unchanged from
   `0007`'s existing threat model, and unchanged by this package.
4. **Most governed *write* paths were already covered by grants**, so the practical reach of the
   old GUC spoof was (a) audit attribution and (b) the **read** policies — where a requester holds
   `SELECT` by design and only `cw.app_role()` kept them inside their own deals. Both are now
   tested. This is stated so the fix is not read as broader than it is.

## 7. Deviations and limitations

- **`0003_ladders_and_concessions.sql:369-376` is now stale prose.** That comment block explains
  why `promote_concession()` is not `security definer`, on the grounds that "the role check reads a
  session variable any client can set". That is no longer true — the role check now reads the
  connection. The reasoning's *conclusion* still holds (invoker rights keep the caller's privileges
  and the row policies in play), but the stated ground has moved. `0003` is outside this package's
  ownership, so it was **not edited**; flagged here for WP-26/WP-28 or whoever next owns `0003`.
  The same sentence recurs at `0003:565-568` above the `revoke ... from public`.
- **`set_config('cw.role', …)` calls survive in six suites** as inert leftovers. They are harmless
  (a custom GUC nobody reads) and several are load-bearing *as spoof attempts* in the new tests, so
  they were left rather than swept. `roles.mjs` — the shared instrument — was cleaned.
- **The JWT-claims accessor is described, not built** (§3), as the packet directed.
- No new dependency. No existing assertion weakened; the one assertion that changed is declared in
  §3 and came out net stronger.
