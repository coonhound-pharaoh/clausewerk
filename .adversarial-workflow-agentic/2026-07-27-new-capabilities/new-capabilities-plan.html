1.

Scope

This plan covers the five new capability areas discussed in the session of 27 July 2026. It does not propose rebuilding anything that already exists. The negotiation database is already built; the audit chain and draft provenance infrastructure are already built; the trust boundary is already built. What follows is what sits on top of them.

The product direction this plan supports: Clausewerk is not an anti-AI tool — it is a responsible-AI tool. The selling point is that every place AI is used is known, documented, reviewed by a named person, and measurably scrutinised. The metrics and compliance scaffolding in this plan are what make that claim provable rather than asserted.

3.

Work Packages

WP-1
Input Module — AI Pipeline Connection
The interface is being finished now; this work connects the pipeline to it

The AI interview pipeline — which conducts the buyer interview and produces a risk manifest — needs a defined way to connect and submit to the system. The manifest-check and assembly-run endpoints it plugs into are part of the approved connection work that is being written right now, so this package starts once that work lands. It adds no endpoints of its own.

One word of vocabulary, settled once: in the system, the buying company is the counterparty and the person running the interview is the requester. The name on the record is the requester's.

An interview conducted by AI produces a risk manifest and a complete contract assembly, with the requester who ran it named throughout the audit record, and the record itself showing that a model produced the manifest. The deliverable includes the case where the model is unavailable — the same run recorded, marked as assembled by the fallback. The integration is tested and documented so any pipeline implementation can connect to it.

After the connection work lands The identity question (D-1) turned out to be mostly already answered — see section 5 Small — days to a few weeks
WP-2
Negotiation Core — API Layer
The database is built; this work opens it up — and closes two permission holes first

Build the API endpoints for the negotiation tables: opening a negotiation, recording each round a document is exchanged, uploading a received redline, and moving positions between states — open, held, conceded, escalated, settled. Escalating a position is the routing mechanism to Legal; it is already a first-class state in the database and needs only an endpoint to trigger it.

The review found this package is bigger than first written. Today the database lets any requester add a negotiation record to somebody else's deal — reading is properly fenced, writing is not. Building screens on top of that would carry the hole into the product, so this package's one database change closes both halves: the five unfenced summary screens (open question 12 — three live in the negotiation work, two in the governance work, one fix covers all five) and the write side. It claims whatever migration number is next free on disk the day it starts — numbers are never promised in a plan, because the newest migration file is not yet committed and a number written down is a number someone reuses.

A buyer can open a negotiation, record every exchange with the counterparty in order, and route any specific point to Legal when needed. Every step is in the audit chain. Legal and the Auditor can see the full history. The position-revival view — which flags a point being re-raised after it was thought settled — is live from the first round.

One dependency to know about: today the system can only send a document, not receive one. The redline-upload part of this package includes teaching it to receive — a small piece, but it touches files the in-flight connection work is editing, so it waits until that work finishes. Everything else in WP-2 can start now.

Ready to start Medium, larger than first estimated — weeks to a couple of months
WP-3
Negotiation Round Analysis
What the system tells the buyer when the supplier's redline arrives

When a buyer uploads a supplier redline, the system processes it through a seven-step pipeline. Parsing the changes and comparing them to the ladder are deterministic. Identifying which negotiating position a change touches, categorising it, assessing its risk, and producing an advisory recommendation are AI-assisted. The fallback rules were already decided and partly built: where matching is uncertain, the system escalates to Legal on a review ticket rather than guessing — a worse automatic match is more dangerous than no match. The deterministic steps live in the core engine, with the service layer adapting to it and never the other way round — the same rule the first AI connection established. Every step is separately visible so a reviewer who disagrees with the categorisation can see it before the alternatives are chosen.

A buyer facing a vendor counter sees: what changed, which ongoing negotiating point it touches, where that position sits on the ladder, what the company has accepted on comparable deals, and the available alternatives ranked from best to floor. An advisory recommendation is attached — clearly labelled as advice, never as a decision. The buyer is never staring at a redline alone.

Added by the owner (27 July): a risk-exposure score — an AI estimate, baselined on the original clause, of the percentage of risk transferred from supplier to customer. It runs in both directions: every proposed move shown in round analysis carries its estimated risk transfer before the buyer chooses, and an accepted concession carries what the choice actually cost. An estimate with its sources cited, never a decision.

After WP-2 WP-2 Large — months; significant AI/pipeline work
WP-4
Supplier Paper
When the vendor's document is the starting point, not ours

When the counterparty provides their own base document, there are no clause IDs to match against. AI decomposes their document into clause-like units — each assigned a category, each quarantined so it can never enter the library or appear in a contract the system assembles. Every unit keeps a reference back to its exact location in the source document. Unknown categories are dropped at the boundary, exactly as in the manifest. Once decomposed, their paper flows through the same round analysis pipeline as a standard redline.

The system handles both directions. A buyer receiving a vendor's standard form gets the same ladder comparison, concession history, and alternative analysis they would get on the company's own paper. Supplier language that has been seen repeatedly across counterparties becomes input to the Library Builder — a pattern the company can choose to address with new approved language.

The decomposition-and-quarantine half does not need the analysis pipeline and can likely begin alongside WP-3; only the "flows through the pipeline" tail waits for it. It shares WP-2's receive-a-document dependency.

Tail after WP-3; first half can start alongside it WP-3 Large — months; AI decomposition work
WP-5
Clause Library Builder
AI drafts; a named lawyer decides; the record proves it

AI drafts candidate clauses and ladder-position proposals from the concession record, identified coverage gaps, and company rules. Each draft lands in the Review queue as a proposal — not a clause. A named lawyer approves, edits, or rejects it. Approving a draft without editing is recorded separately from approving one that was changed. The full provenance of every draft — which model, which version, what it was shown — is stored permanently and is part of the audit chain. A draft may not be approved by whoever requested it when the requester is not Legal.

Less new than it looks: the library-proposal surface, the AI-drafted origin marker, and the draft record with its provenance all exist today. This package builds on them rather than inventing them.

The clause library can grow at business speed. Coverage gaps that currently produce a hard failure at assembly time can be filled without waiting for lawyers to compose language from scratch. But an approved draft is only useful if it can be put into service — activating a clause and promoting a concession are two of the six missing governance controls, which is why decision D-5 sits in front of this package.

Needs D-4 and D-5 first D-4 D-5 Can run parallel to WP-3 once the draft-record fields are agreed Large — months
WP-6
Edit Quality Metrics and Customer Thresholds
How much did Legal actually change the AI draft?

At the moment a draft is approved, the system computes the similarity between the original AI text and the approved text and stores it permanently with the draft's record — where the before-and-after already lives — rather than on the approved clause itself, whose provenance fields are locked against change. One rule matters more than any other here: the figure is computed by the database at the moment of approval, never supplied by the software calling in — the same discipline that already protects the unedited-approval rate from being gamed. This produces the new metric: average percentage of original AI language retained across the library, by clause category, and per contract. Customer-configurable thresholds are added as governance settings, consistent with the existing settings model.

Legal leadership can see not just whether AI drafts are being reviewed, but by how much. A company that sets its own thresholds can demonstrate to a regulator that they have been monitored and met, with the evidence in the system record rather than assembled from email. Thresholds are chosen by customers, not preset by the product — measured from day one, no threshold until Legal sets one, the posture you already decided.

Good news from the review: this package moved a whole phase earlier. The database already keeps the before-and-after text for every AI draft, so this does not have to wait for the Library Builder — only for the draft-record design session (D-4).

Added by the owner (27 July): alongside the arithmetic score, an AI semantic-difference measurement — how much the meaning changed between the AI draft and the approved text. It is an AI judgment, so it follows the judgment rules: stored with its provenance, labelled an estimate, never supplied by the calling software, and shown beside the measurement, never in place of it.

Needs D-4 only — earlier than first planned D-4 Small — weeks
WP-7
EU AI Act Compliance Scaffolding
Compliance evidence lives in the tool — provable, exportable, not reconstructed

Extend the draft record with the additional fields EU documentation requirements ask for — intended purpose, known limitations at time of use, and model performance metrics. Most of what a regulator asks about is already stored: the prompt, the model, its version, and what it was shown are on every draft today, so the schema work is three new fields, not a new record. Build a compliance export — a machine-readable package covering every AI use instance, who reviewed it, what they changed, and the evidence of meaningful oversight. Wire customer-configurable disclosure into the review interface. Build to the high-risk standard regardless of initial classification; the cost of building higher is small and the cost of retrofitting is not.

A customer demonstrating responsible AI use to a regulator, an auditor, or a prospective client hands them an export — not a reconstruction from email threads. All documentation requirements, approval and review processes, and evidence of human oversight occur inside the tool and are provable from the audit chain. This is a product differentiator, not a compliance burden.

One decision this surfaces (D-6): we promise customers a full record of every AI use, and we also promise we can delete data on request. Those two promises meet in this export, and which one wins for a deleted record is your call, not engineering's.

After D-2, D-4, and D-6 D-2 D-4 D-6 Medium, then ongoing as regulations develop
WP-8
Contract Intelligence — Portfolio Questions Across All Paper
"How many contracts have an uncapped confidentiality damages limit?" — answerable whatever paper it's on

A searchable index over every contract in the system, so portfolio-wide questions can be answered no matter whose paper the contract is on and no matter how the supplier edited our language. It has two halves, because the system already knows two different amounts about its contracts. For contracts assembled on our own paper, the run record already says exactly which clause and which ladder rung is in each one — those questions are answered precisely from the database, no AI involved. For supplier paper and supplier-edited language, the decomposed clause units WP-4 produces (each categorised, each pointing back to its exact place in the source document) are embedded into a vector index; a question finds the matching clauses by meaning rather than wording, and an AI step assesses each match, with every assessment citing its source so a person can check it.

Legal can ask a question across the whole book of contracts and get an answer in two clearly-labelled parts: a certain count from contracts on our paper, and an AI-assessed count from supplier paper — each one traceable to the exact clauses behind it, never a bare number. This is the same responsible-AI posture as the rest of the plan: the system shows its work.

Two things are yours to decide before it ships (D-7): who may ask portfolio-wide questions — a requester fenced to their own deals must not get counts computed across everyone else's — and the index must honour the deletion promises: when a contract's content is removed, its traces leave the index too, which is part of the D-6 question.

After WP-4 and D-7; disposal answer shared with D-6 WP-4 D-6 D-7 Medium–Large — months; AI and search work

5.

Decisions Required

The review resolved two of the original four decisions from the record. Five remain open: D-2, D-4, D-5, D-6, and D-7.

D-1 · mostly answered AI pipeline identity — the system already decided most of this

The record always carries the name of the person the system is connected as — there is nowhere to put a second name, and we decided long ago not to let software act under a shared account. So the AI interview runs under the requester, and the record separately shows whether a model, the fallback, or a person produced the manifest. No decision is needed for WP-1 to proceed.

The one genuinely open piece: today, signing in doesn't prove who you are — that arrives when a real identity provider is connected. How the pipeline holds a person's credential at that point is an open question to settle during the identity-provider work, not now.

Blocks: nothing
D-2 EU AI Act risk classification — needs counsel's read

Is the system classified as high-risk or limited-risk under the EU AI Act? The classification determines documentation requirements. Contract management tools that touch legal processes may fall under Annex III (high-risk); the answer depends on how the tool is used and in which jurisdictions.

Recommendation: Commission counsel's read before the compliance scaffolding is designed. Build WP-7 to the high-risk standard regardless — the incremental cost is small and there is nothing to retrofit if the classification changes later.

Blocks: WP-7
D-3 · already settled by you Metric threshold defaults — you already ruled on this

The earlier draft recommended shipping with preset default numbers. The review found that contradicts a decision you already made: the unedited-approval threshold is deliberately unset, because picking a legal review standard is content, and the system must never choose that number. The new metric follows the same posture.

Standing answer: measured from day one, no threshold and no alarm until Legal sets one with counsel. Nothing is blocked on it.

Blocks: nothing
D-4 Draft record fields — one session, smaller than first thought

The Library Builder (WP-5), the edit quality metrics (WP-6), and the EU compliance scaffolding (WP-7) all depend on what the draft record carries. Most of it already exists — every draft already stores its prompt, model, version, and what it was shown. The session only has to agree the few new fields (the similarity score, and the three EU documentation fields). Getting it right up front still matters, because draft records can never be changed once written.

Recommendation: One design session covering WP-5/6/7's needs together, before the first database change that touches the draft record. It blocks those database changes — not all work on the three packages.

Blocks: the WP-5 / WP-6 / WP-7 database changes
D-5 · new The six missing governance controls — in this effort, or a follow-on?

Six governed acts exist in the database but have no way to be performed: activating/retiring a clause, superseding a clause, editing a conflict rule, promoting a concession, reordering a ladder rung, releasing a legal hold, and retention destruction. Two of them — retention destruction and clause supersession — you have already decided, and they only need their endpoints built. The other four still need your ruling. The clause library (WP-5) is not much use without clause activation and concession promotion.

Recommendation: Decide whether the six belong to this effort or a named follow-on. If in: the two already-decided ones can start today; the four open ones need a short owner session first.

Blocks: WP-5's usefulness
D-6 · new When "record everything" meets "delete on request" — which promise wins?

The compliance export promises a full record of every AI use. The system also promises it can remove data on request — and by design, the tamper-evident audit trail survives every removal and can never be deleted. The first compliance export a customer runs will either report AI uses whose content they believe was removed, or leave them out and under-report. Nobody has decided which.

Recommendation: Decide before WP-7's export is designed. This is a product-promise question, not an engineering one — likely worth putting to counsel alongside D-2.

Blocks: WP-7's export design
D-7 · new Portfolio questions — who may ask across all contracts?

WP-8 lets a person ask a question whose answer is computed across the whole book of contracts. Today every role is fenced: a requester sees only their own deals. A portfolio answer — even just a count — reveals something about everyone else's deals. Who gets to ask: Legal only? Legal and the Auditor? Requesters for their own slice?

Recommendation: Legal and the Auditor across the book; a requester may ask the same questions scoped to their own deals only. Same fencing principle the rest of the system already follows — decided by you, enforced by the database, before the first index is built.

Blocks: WP-8

What This Revision Changed, and Why

An adversarial review — three independent verification passes and three challenge passes, every claim checked against the codebase — changed the following. Everything below survived at least one deliberate attempt to disprove it.

  • WP-1 moved out of Phase 1. The endpoints it plugs into are not finished — they are being written this week by the already-approved connection work. Starting WP-1 beside it would put two efforts in the same files.
  • WP-2 grew. The database currently lets any requester add negotiation records to another person's deal. The same class of hole was just closed for assembly runs; WP-2's database change closes it here, on top of the five-screen read fix already planned.
  • WP-6 moved a phase earlier. The before-and-after text it measures is already stored for every AI draft. It never needed the Library Builder — only the D-4 design session.
  • D-1 mostly dissolved. The architecture already forces the answer the plan recommended; the only genuinely open piece is deferred to the identity-provider work.
  • D-3's recommended numbers were deleted. They contradicted your settled decision that the system must never choose a legal review standard.
  • Two new decisions surfaced: whether the six governance controls are in scope (D-5), and which wins when the compliance record meets a deletion request (D-6).
  • A stale gap was removed: the "two unaudited writes" were fixed on 20 July.
  • A missing dependency was named: the system can send a document but cannot yet receive one; WP-2's redline upload and WP-4's supplier paper both need that taught, after the connection work finishes.
