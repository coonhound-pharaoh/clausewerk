# NC-05 — A person may not approve their own request · implementation report

Date: 2026-07-27. Owner: single-owner implementer for NC-05. Not committed.

## What was built

The database now refuses to let the person who opened a request for new contract language
also approve it, unless that person is themselves Legal. The refusal lives inside
`cw.verify_review_ticket()`, beside the role check that was already there, so a caller
arriving by any other path meets the same wall. No role or name logic was added to any
endpoint.

## The rule, and how it is bounded

- Refuse when the person deciding is the person named in `cw.review_ticket.opened_by`.
- Both the connection's actor (`cw.app_actor()`) and the reviewer named on the call
  (`p_reviewer`) are compared, because either alone can be routed around — the doorway
  passes the connection's actor as the reviewer, so a call where the two disagree is
  exactly the shape worth stopping.
- Carve-out, as the plan requires: if the opener holds an effective role of
  `legal_reviewer` or `legal_admin`, they may still decide their own ticket. Legal opening
  and deciding in Legal's own queue is Legal doing its work.
- "Is the opener Legal?" is answered by `cw.effective_role` — the system's own authority on
  what a person may do right now — and by nothing else. If the opener has no effective role
  there, the system cannot show the opener was Legal and the conservative answer is the
  refusal. This is stated plainly in the migration header.
- Everything else in the function is carried forward byte for byte from
  `0009_clause_origin.sql:189-255`: minting, origin derivation, the rowcount check.
- The prior function body is quoted verbatim in the migration's reverting footer.
- No mutation-check row was added: no Python line is guarded here.

## Acceptance criteria

| Criterion | Result |
|---|---|
| A test proves the opener of a requester-originated ticket cannot verify it, and that the refusal comes from the function | PASS |
| A test proves a Legal reviewer can still verify a Legal-opened ticket | PASS (the bootstrap Legal admin) |
| A test proves the existing role refusal still holds for every other role | PASS (viewer, requester, auditor, administrator) |
| The existing review-queue tests pass unchanged | PASS — `review-queue.test.mjs` 43/43, file untouched |
| No test asserts on the refusal's wording | PASS — refusals are asserted by outcome only |

On "the refusal comes from the function": an error alone would look the same as a missing
grant, so each refusal is paired with a control — the identical call by a person who did
not open the ticket succeeds and mints — and with a state check that the ticket is still
pending and no clause version exists.

## Deviations

One: the migration number moved from 0027 to 0028 mid-flight because another package claimed
0027 concurrently. Nothing else deviates from NC-05's scope or target-file list.

One judgement call worth naming for the record: NC-05 says to bound the rule on the requester-originated case but the ticket table stores no
opener role, so the opener's role is derived from `cw.effective_role` at decision time, and an
opener the system holds no effective role for is refused rather than waved through.
