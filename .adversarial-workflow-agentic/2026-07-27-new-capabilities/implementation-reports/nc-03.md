## What the migration does

`create or replace` of `cw.open_renewal` only. Everything from `chosen :=`
onward is the 0011 text character for character; the prior body (0011:226-300)
is quoted verbatim in a reverting footer. Grants, arguments, return type and the
`security definer` property are unchanged.

Added, as the first statement in the function body:

- Legal branch, unconditional: `cw_legal_reviewer`, `cw_legal_admin`.
- Requester branch: `cw_requester` **and** `cw.owns_agreement(p_agreement_id)` —
  the same expression 0027's four insert policies use, asked of the same column.
- Otherwise `raise exception` with `errcode = 'insufficient_privilege'` (42501),
  which is the code `backend/doorway/refusals.py:88-89` classifies as
  `not_permitted` / 403.

**One thing worth the owner's attention.** `cw.app_role()` could not be used
here. Inside a SECURITY DEFINER function PostgreSQL replaces `current_user` with
the function's owner, so `cw.app_role()` answers about the definer, returns
null, and a branch comparing null to a role name is neither true nor false —
which is exactly the fail-open guard 0023:145-152 already paid for in the
redaction path. This was confirmed empirically against PGlite before the check
was written. The caller is therefore identified from
`current_setting('role')` (set by the `set local role` the doorway uses and the
`set role` the test helper uses), falling back to `session_user`. Both paths
were reasoned about and the reasoning is in the migration header.

Consequence, stated in the header rather than left to be discovered: the
database owner holds no application role and so can no longer call this
function. That matches settled decision U3, which already gives the owner
nothing through the scoped views.

**U1 untouched.** The check changes who may open a renewal. Both baseline
branches, the drift report and the audit payload are unchanged, and a test
asserts a renewal still opens from the positions in force.

## The mutation repoint, and why

The harness refused to run at all — correctly. The row named *"the
executed-agreement baseline is not actually built"* had the find string
`  if chosen = 'executed_agreement' then`. 0031 replaces the function wholesale
and quotes the prior body in its reverting footer, and the footer's lines carry
that body verbatim behind a `--   ` prefix, so the pattern matched **twice inside
0031** and tripped the harness's at-most-once-per-file invariant.

Repointed, not deleted, per the harness's own live-definition rule: the find
string now begins with a newline, which the live branch has and the
comment-prefixed copy does not. It still matches both live definitions, 0011's
and 0031's — which is required, since 0031 runs last and an unmutated copy there
would silently cancel the mutation (the harness calls this trap 5.4a). The
reason is written into the harness beside the row.

No other mutation pattern was affected; preflight named only this one.
