# NC-25 — Advisory judgments: the record, the model seam, and the semantic-difference score

Implementation report · 2026-07-27 · branch `assembly-connection-2026-07-27` · not committed

## What was built, in plain words

The system already measures how far the words Legal approved are from the words the model wrote.
That figure counts words. It says "a person worked on this" and it says nothing about meaning.

This package adds the second thing beside it: an AI's opinion of how much the **meaning** changed —
and, more importantly, the machinery that keeps an opinion from ever being mistaken for a
measurement. An opinion now has its own permanent record, its own labels, and one honest way to
say "there isn't one".

Three parts:

1. **A record of its own.** `cw.advisory_assessment` — append-only, provenance-complete, holding
   the ticket, the two texts the model was shown, the judgment, the model, its version, the prompt,
   who asked and when. Nothing about the frozen draft or ticket rows changed.
2. **The model seam.** One module, `backend/doorway/advisory.py`, is the only place in the product
   that asks a model for an opinion. When there is no key, or the model cannot be reached, it
   records **no judgment, with the reason** — never a substitute number, and never a delay to the
   person's real work.
3. **A board that keeps the two apart.** A metrics view shows the measurement and the estimate side
   by side, each carrying its own label, so no screen can present them as the same kind of thing.

### The database mutation row that is stale, and why it is not this work

`db/test/mutation-check.mjs` mutates `cw.review_ticket_transition()` by finding a five-line block
and replacing it. **0029 (NC-11) redefines that whole function with `create or replace`**, and 0029
loads after 0008. Checked rather than assumed: the row's exact block appears **once in 0008 and zero
times in 0029**. The harness therefore mutates a definition that 0029 immediately overwrites, the
running schema never sees the change, and the named test correctly passes — which the harness
scores, correctly, as unguarded.

Nothing in NC-25 can reach this. `0030` defines no function that `0008` or `0029` owns; it adds one
table, one view and triggers on its own table. The row was stale the moment 0029 landed. Fixing it
belongs to whoever owns NC-11's migration — the block simply needs re-pointing at 0029's copy — and
it is deliberately not taken here, because a package that quietly repairs another package's
mutation row hides the fact that the guarantee has been unguarded since 0029 merged.

### The doorway mutation row that did not come back clean, and why it is not this work

Row 1 mutates `doorway/db.py` and names a test in `test_writes.py`. Neither file was touched by this
package. The harness's own docstring describes the cause: the mutation lanes are not fully isolated
(`setup.py` runs a cluster-wide `alter role`), so concurrent rebuilds collide and a lane that dies in
its fixture never evaluates its guarantee — which the harness now scores `IMPRECISE` rather than
letting it read as protection.

Checked rather than assumed: the mutation was applied by hand to a copy of the tree and the named
test run on its own. It **failed, on its own assertion** (`unrecognized configuration parameter
"cw.actor"`). The guarantee is guarded; the harness verdict is a concurrency artefact of this
machine, not a hole, and it is not caused by the row this package added.

`npm run verify` therefore exits non-zero inside `test:mutation` for two pre-existing reasons — the
stale database row above, and this concurrency artefact. Every other stage is green, and both new
suites pass.

## Where the package text and the repository disagreed, and how it was ruled

**1. "The caller never supplies a score" (scope) vs "a caller-supplied score is ignored"
(acceptance).** Two different enforcements. The D-4 precedent — `edit_similarity` is computed by the
database and overwrites whatever was sent — only settles the case where the database can compute the
value itself. It cannot compute an opinion; nothing in the schema can.

*Ruled: both, at the layer each belongs to.* The doorway **ignores** it — `advisory.py` drops
`score`, `basis`, `outcome`, `model` and `model_version` from the request body before a single line
reads it. The database **refuses** it — an `absent` row cannot carry a score, and a `recorded` row
cannot exist without a model, a version, a prompt and a score. A number typed by a caller has
nowhere to land. Written out in the migration header.

**2. "The metrics view gains the latest semantic judgment beside the arithmetic figure."** There is
no per-ticket metrics view in the repository. `cw.review_quality` is an aggregate rate and
`GET /quality` reads it; the arithmetic figure NC-11 added lives on `cw.review_ticket`. *Ruled:*
the migration creates `cw.ticket_metrics` (one row per ticket, both figures, both labels, the latest
judgment plus a count of the history) and `reads.py` gains `GET /metrics`. Nothing existing moved.

**3. The view scoping trap.** A PostgreSQL view runs with its **owner's** rights and row-level
security is enabled rather than forced, so a new view over `cw.review_ticket` would have handed
every requester every ticket in the system. This repository has paid for that shape three times and
keeps a standing guard for it (`db/test/views-are-not-policies.test.mjs`). `cw.ticket_metrics`
therefore carries `cw.review_ticket`'s own read rule in its `WHERE` clause, verbatim — not
`security_invoker`, for the reason `0017` and `0019` already wrote down. A test proves a requester
sees their own ticket on the board and not a stranger's.

**4. `cw_administrator` is deliberately not granted the board.** Following the precedent `0025` set
for this same role: the administrator's read boundary is an owner decision about a role, and
settling it inside a feature migration puts a new control where nobody would look for it. The
`WHERE` clause names no `administrator` branch for the same reason — a branch that can never execute
is reassuring text.

**5. `actor_kind`.** The audit entry was first written as `'model'`. `0001` allows only
`human`/`controller`/`system`, and reserves `controller` for acts taken *without* a human. A named
person asks for a judgment, so the entry is `human` and whose opinion it is lives in the payload.

**6. ADR-0005 bends here, and it is stated where it bends.** Every earlier inference has a
deterministic substitute. A judgment does not — no regex estimates how much a meaning moved, and one
that produced a plausible number would manufacture exactly the false confidence the ADR exists to
prevent. The substitute is the honest one: the absence is recorded as a fact, and the caller's real
work is never blocked. Written into the module docstring and the migration header rather than left
as an unexplained departure.

## Content discipline

No test in either new suite asserts on a judgment's wording or its value. Where a judgment must be
shown to be present, presence is asserted; where the board's two labels must be distinguishable,
they are asserted to be **different from each other**, never to say any particular thing. The prompt
is content and is placeholder pending Legal's review — it is stored verbatim on every row so that a
later review can tell which wording produced which past judgment.

## Deviations from the package

- **`GET /metrics` is a new read rather than an addition to an existing metrics view** — there was
  no such view. See ruling 2.
- **`mutation_check.py` gained exactly one row**, per the brief: the ADR-0005 guarantee, consumed by
  a named test. No row was added for the caller-score rule, because that guarantee is guarded by a
  database constraint rather than by a line of Python, and a mutation row that names no consuming
  line would be the stale check the harness treats as worse than a missing one.
- **`risk_exposure` is already in the judgment-kind allow-list.** Out of scope to implement, and
  listing it now means NC-26 appends rows rather than a column.
